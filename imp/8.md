# PROMPT 08 — Indie Sign SEO, Performance, Responsive QA, and Deployment Preparation

## 1. Role and Objective

Act as a senior frontend performance engineer, technical SEO specialist, accessibility tester, and deployment engineer.

Continue the existing Indie Sign project.

Do not rebuild the project from scratch.

First inspect the existing source code, package.json, routes, assets, document-generation system, LocalStorage architecture, and previous implementation.

Improve the current application so it is production-ready for deployment as a static React website.

Preserve all existing functionality:
- Home page.
- Portfolio.
- Services.
- About.
- Contact.
- Price Calculator.
- Owner Settings and PIN gate.
- Quotation, Invoice, and Receipt PDF generation.
- Quote History.
- JSON backup and restore.
- Light and dark themes.
- Floating WhatsApp contact button.

Do not introduce a backend, external database, or paid service requirement.

## 2. Technical SEO

Implement and verify:
- Unique page titles.
- Appropriate meta descriptions.
- Canonical URLs when the production domain is configured.
- Open Graph metadata.
- Social sharing preview metadata.
- Favicon and site icons.
- Descriptive image alt text.
- Correct heading hierarchy.
- Descriptive internal links.
- Lao-language metadata where appropriate.
- `robots.txt`.
- `sitemap.xml`.
- A web manifest only if appropriate for the existing application.

Use Lao keywords naturally for signage services in Laos.

Possible keyword themes include:
- ຮັບເຮັດປ້າຍ.
- ອອກແບບປ້າຍ.
- ຜະລິດປ້າຍ.
- ຕິດຕັ້ງປ້າຍ.
- ພິມສະຕິກເກີ.
- ປ້າຍໄຟ.
- ນາມບັດ.

Do not stuff keywords unnaturally.

Do not invent business addresses, service areas, customer reviews, certifications, or claims that are not present in the project.

Allow the owner to configure the production site URL and relevant SEO metadata.

Do not use localhost or a development URL as the production canonical URL.

Do not promise Google indexing or ranking.

## 3. React SEO Compatibility

Inspect the existing routing and rendering architecture.

If the project uses client-side React rendering, implement page metadata appropriately and explain the limitations of client-rendered SEO.

Do not claim that adding metadata alone guarantees search indexing.

Do not migrate to a new framework or introduce server-side rendering unless there is a compelling technical reason and the change is explicitly justified.

Keep the current React + Vite architecture whenever possible.

Ensure route-specific titles and descriptions update correctly during navigation.

## 4. Robots and Sitemap

Create valid `public/robots.txt` and `public/sitemap.xml`.

Requirements:
- Use the configured production domain.
- Do not include localhost.
- Include only intended public pages in the sitemap.
- Exclude Owner Settings, internal quote history, and other private application routes.
- Exclude query parameters and temporary URLs.
- Avoid claiming that robots.txt is an access-control mechanism.
- Do not use robots.txt as a substitute for protecting private pages.

If the production domain is not yet known, provide a clearly documented placeholder and instructions for replacing it before deployment.

Do not fabricate a domain.

## 5. Search Console and Analytics

Integrate with the existing Owner Settings fields where available.

Support optional:
- Google Search Console verification value.
- Google Analytics measurement ID.

Requirements:
- Do not load analytics when no valid measurement ID is configured.
- Avoid duplicate analytics initialization.
- Do not expose unrelated settings.
- Do not record sensitive customer information or quote contents in analytics events.
- Document how to verify ownership and submit the sitemap manually.
- Keep analytics optional.

Do not create a custom analytics dashboard.

## 6. Performance Optimization

Audit and improve:
- JavaScript bundle size.
- Unnecessary dependencies.
- Duplicate libraries.
- Unnecessary component re-renders.
- Large images.
- Image loading strategy.
- Font loading.
- CSS delivery.
- Route-level code splitting where appropriate.

Portfolio requirements:
- Use compressed images.
- Prefer WebP or another suitable modern format when supported.
- Use appropriate image dimensions.
- Add width and height or aspect-ratio constraints to reduce layout shift.
- Lazy-load off-screen portfolio images.
- Do not lazy-load the main hero image if doing so harms the initial display.
- Preserve image quality suitable for showcasing signage work.

Use existing files in `public/images/portfolio/`.

Do not invent portfolio images or delete user-provided images.

If an asset is missing, provide a fallback and report the missing path.

Do not add unnecessary animations or libraries that harm performance.

## 7. Responsive Design and Accessibility

Test and refine the application at representative viewport widths:
- 320px.
- 375px.
- 768px.
- 1024px.
- 1440px.

Check:
- Navigation and mobile menu.
- Home hero.
- Portfolio gallery.
- Calculator forms and item tables.
- Document preview.
- Owner Settings sidebar.
- History table and search.
- Dialogs and forms.
- Floating WhatsApp button.
- Footer.
- 404 page.

Fix:
- Horizontal overflow.
- Clipped text.
- Buttons too small for touch.
- Forms that exceed screen width.
- Tables that cannot be used on mobile.
- Overlapping floating controls.
- Broken light/dark theme styles.

Accessibility requirements:
- Semantic HTML.
- Keyboard navigation.
- Visible focus indicators.
- Correct form labels.
- Appropriate contrast.
- Useful image alt text.
- Accessible dialogs.
- Reduced-motion support where relevant.

Do not redesign the entire application unnecessarily.

## 8. Security and Privacy Review

Review the static application for accidental exposure of sensitive information.

Verify:
- No secrets or API keys are committed to client-side code.
- No private customer details are hardcoded.
- No customer data is sent to analytics.
- Owner-only routes have the existing basic PIN gate.
- The documentation explains that client-side PIN protection can be bypassed.
- The application does not falsely imply that LocalStorage is secure or synchronized.
- JSON restore validates data before replacing existing records.
- User-supplied text is rendered safely and not interpreted as executable HTML.
- External links use appropriate safe link attributes where applicable.

Do not claim that frontend-only route guards provide strong security.

Do not add a backend in this step.

## 9. Error and Empty States

Review all major pages for:
- Loading states.
- Empty portfolio state.
- Empty quote history state.
- Missing images.
- Invalid calculator input.
- PDF generation errors.
- LocalStorage unavailable or full.
- Invalid JSON backup.
- Unavailable optional analytics configuration.
- Unknown routes.

Ensure the 404 page follows Indie Sign branding and includes navigation to Home and Calculator.

Do not add a Back to Top button.

## 10. Production Build and Environment Configuration

Inspect and improve the production build process.

Requirements:
- Correct Vite production configuration.
- Correct environment-variable usage.
- No hardcoded development-only URLs.
- No missing imports.
- No TypeScript errors.
- No broken public asset paths.
- No runtime errors caused by missing optional configuration.
- Correct route handling for the selected static hosting platform.
- Document the commands needed to install dependencies, run development mode, and build the project.

Use environment variables only for non-secret public configuration.

Never put private credentials in Vite client-side environment variables.

Check that all necessary production assets are included in the build.

## 11. Static Hosting Readiness

Prepare the application for a free static hosting provider compatible with Vite.

Do not deploy automatically or create an account on the user's behalf.

Provide a deployment guide covering:
1. Installing project dependencies.
2. Running the local development server.
3. Running the production build.
4. Previewing the production build locally.
5. Uploading the project to a Git repository.
6. Connecting the repository to a compatible free static host.
7. Configuring the build command.
8. Configuring the output directory.
9. Handling React Router direct URLs and page refreshes.
10. Configuring the production domain.
11. Verifying HTTPS and the public website.
12. Testing Calculator, PDF generation, Owner Settings, and LocalStorage after deployment.

Explain that browser-stored data belongs to the visitor's browser. A public static site does not provide shared business storage between customers, browsers, or devices.

Explain that owner settings and saved quote history remain local to the browser unless the architecture is later upgraded with a backend.

Do not promise that all hosting providers offer identical free-tier features.
