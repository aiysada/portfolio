PROMPT 06 — Indie Sign Owner Settings, PIN, and JSON Backup
1. Role and Objective
Act as a senior React, TypeScript, frontend architecture, and local-data management engineer.
Continue the existing Indie Sign project without rebuilding it.
Inspect the current implementation before making changes.
Reuse the existing:
React + Vite + TypeScript setup.
shadcn/ui components and design tokens.
React Router routes.
Price Calculator and pricing data models.
PDF document generation system.
LocalStorage utilities.
Light and dark theme support.
Implement a complete Owner Settings area that allows the owner to manage products, pricing rules, business information, document settings, and local data backups without editing source code for routine changes.
All existing public pages and calculator features must continue to work.

3. Owner PIN Login
Create a PIN login screen for the Owner Settings area.
Requirements:
Use a configurable default PIN stored in project configuration.
Allow the owner to change the PIN after entering the current PIN.
Never display the PIN in plain text by default.
Provide show/hide PIN input functionality.
Add a temporary lockout after repeated incorrect attempts.
Provide a logout action.
Protect owner routes and owner-only UI actions from casual access.
Persist appropriate authentication state locally without keeping the PIN in browser storage as plain text.
Clear owner authentication state on logout.
Important security limitation:
This is a frontend-only application with no backend authentication. A client-side PIN is only a basic access barrier and must not be described as strong security. A person who can inspect or modify the application files or browser data may bypass it.
Do not claim that the PIN protects data from a technically capable attacker.
Do not invent server-side authentication or APIs.

12. JSON Restore and Validation
Allow the owner to select a JSON backup file and preview its basic metadata before restoring.
Validate:
File type and readable JSON.
Application identifier.
Backup schema version.
Required data structures.
Product and pricing field types.
Document history structure when present.
Unexpected or unsupported schema versions.
Before replacing any existing data:
Show a confirmation dialog.
Explain that restoring will replace the corresponding current browser-stored application data.
Recommend exporting a backup first.
Allow the owner to cancel.
Restore atomically where practical:
Validate the entire payload first.
Do not partially overwrite data when validation fails.
Preserve the existing data if the file is invalid.
Apply a controlled migration if the backup version is supported.
Notify the user in Lao when restoration succeeds or fails.
Do not import an active authenticated session or plaintext PIN.
After a successful restore, refresh application state safely so all relevant pages show the restored data.
13. Storage Warnings

Explain that JSON backups include browser-stored application data and portfolio metadata, but not actual image files stored in the project folder.
Do not imply that LocalStorage data automatically synchronizes between devices.
Do not add a backend or cloud synchronization.
