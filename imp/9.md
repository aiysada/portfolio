# PROMPT 09 — Indie Sign Final Quality Assurance and Bug Fixing

## 1. Role and Objective

Act as a senior QA engineer, React + TypeScript engineer, application security reviewer, and release engineer.

Your task is to audit and stabilize the existing Indie Sign application before deployment.

Do not rebuild the project.
Do not redesign working pages unnecessarily.
Do not remove features to make tests pass.
Do not start a new feature-development phase.

Inspect the complete current codebase and identify real defects, missing implementations, inconsistent data flows, broken interactions, and production risks.

Fix verified problems and report any issues that cannot be resolved.

## 2. Protect Existing Work

Before making changes:
- Inspect Git status if Git is available.
- Review the project structure and package.json.
- Inspect the existing routes, shared types, data utilities, calculator, PDF generation, owner settings, history, backup system, and SEO configuration.
- Identify existing tests and scripts.
- Preserve user-created assets and portfolio images.
- Do not overwrite existing configuration blindly.
- Do not delete working features.

If the project contains uncommitted user changes, preserve them.

Do not run destructive commands such as deleting project folders or resetting Git history.

## 3. Project Build and Code Quality

Run the available project checks, including:
- Dependency and configuration inspection.
- TypeScript checking.
- ESLint, if configured.
- Unit tests.
- Production build.
- Dependency consistency checks.

Inspect:
- Missing imports.
- Incorrect exports.
- Type mismatches.
- Invalid React hooks usage.
- Broken route imports.
- Unhandled promise rejections.
- Runtime errors.
- Invalid asset paths.
- Missing environment variables.
- Unnecessary dependencies.
- Incorrect browser-only APIs used during module initialization.

Fix errors introduced by the application code.

Do not automatically upgrade every dependency to the latest version.

Do not hide TypeScript errors with widespread `any`, `@ts-ignore`, or disabled lint rules.

If a check cannot run because a required tool is missing, report that limitation honestly.

## 4. Price Calculator Verification

Inspect the actual calculator implementation and its shared pricing utilities.

Verify:
- Millimeters convert correctly to centimeters and meters.
- Width and height produce the correct area.
- Quantity is applied correctly.
- Per-square-meter pricing is correct.
- Per-item pricing is correct.
- Fixed pricing is correct.
- Manual pricing works.
- Minimum charge per line item works.
- Multiple line items calculate correctly.
- Design, labor, installation, delivery, and additional services are included correctly.
- Percentage and fixed discounts work correctly.
- Tax applies according to the configured rules.
- Zero values are handled correctly.
- Invalid numeric inputs are rejected safely.
- LAK formatting is consistent.
- All displayed totals use the same calculation source.

Use independent test cases and expected numerical results.

Required example:
- Black-back vinyl: 130,000 LAK/m².
- Width: 200 cm.
- Height: 100 cm.
- Quantity: 2.
- Expected area per item: 2 m².
- Expected subtotal: 520,000 LAK before other charges.

Add tests for edge cases, including zero dimensions, empty inputs, decimal dimensions, and invalid negative values.

Do not invent a minimum price. Use the configured application setting.

## 5. Document and PDF Verification

Test Quotation, Invoice, and Receipt generation.

Verify:
- Correct document type and number prefix.
- Correct issue date.
- Correct item descriptions.
- Correct dimensions and quantities.
- Correct subtotals and fees.
- Correct discounts and tax.
- Correct final totals.
- Correct amount received and remaining balance.
- Correct configured business details.
- Correct logo and font paths.
- Correct page sizes and margins.
- Correct long-document pagination.
- No clipped or overlapping content.
- PDF downloads open successfully.
- Print layout is usable.

Inspect actual generated PDF files when the environment allows it.

Check Lao glyph rendering using the real PDF output, not only browser screenshots.

If PDF inspection or browser automation is unavailable, explain what was tested and what still needs manual verification.

Do not claim successful PDF generation based solely on a successful build.

## 6. Historical Data Integrity

Test the following workflow:
1. Create a quote.
2. Save it to history.
3. Change a product price.
4. Reopen the historical quote.
5. Regenerate its PDF.

Verify that historical quantities, prices, fees, discounts, tax, and totals remain unchanged.

Check that editing a current quote does not silently overwrite an already-issued historical document.

Verify that document numbering does not accidentally duplicate numbers during normal sequential use.

Do not claim globally unique numbering across multiple browsers or devices when there is no backend.

## 7. LocalStorage and Data Migration

Inspect the versioned local-data schema.

Verify:
- First-run defaults initialize correctly.
- Existing data is preserved.
- Invalid stored JSON is handled gracefully.
- Unsupported schema versions are handled safely.
- Missing fields receive appropriate defaults.
- Storage quota errors do not crash the entire application.
- Saved settings persist after refreshing the page.
- History persists after refreshing the page.
- Changes are reflected consistently across relevant components.
- Theme preferences work as intended.

Do not clear LocalStorage as a routine testing shortcut on the user's actual browser.

If tests require resetting storage, use an isolated test environment.

## 8. Backup and Restore

Verify:
- Exported JSON is syntactically valid.
- The backup includes supported settings and history.
- Plaintext PINs and active authentication sessions are excluded.
- Actual image files in the project folder are not falsely represented as included in the JSON backup.
- Import validates the application identifier and schema.
- Invalid files do not overwrite existing valid data.
- Unsupported versions are rejected or migrated safely.
- A confirmation is required before replacement.
- Failed restore operations preserve current data.
- Successful restore updates the UI correctly.

Test export and restore using representative sample data in an isolated environment.

## 9. Owner PIN and Security Review

Verify:
- Correct PIN permits access.
- Incorrect PIN is rejected.
- Repeated incorrect attempts trigger the configured temporary lockout.
- Logout clears the active owner session.
- PIN changes require appropriate verification.
- Owner-only controls are not accidentally exposed in the public navigation.
- User-entered text is rendered safely.
- External links are handled safely.
- No secret credentials are embedded in public client code.
- No sensitive customer data is sent to analytics.

Document that frontend-only PIN protection is a basic barrier, not strong security.

Do not claim the application is secure against a technically capable attacker when data and checks run entirely in the browser.

Do not introduce a backend or external security service in this phase.

Test every available public route:
- Home.

Test:

- WhatsApp link.

- Add, edit, and remove quote line items.
- Document preview and download.
- History search and filters.

- Theme toggle.
- Mobile menu.
- Form validation.
- Confirmation dialogs.

Check that every visible button performs its advertised action.

Remove or fix inert buttons and placeholder links that look functional but do nothing.

Do not remove intentionally disabled features without explaining why.

## 11. Responsive and Accessibility Testing

Test representative viewport widths:
- 320px.
- 375px.
- 768px.
- 1024px.
- 1440px.

Inspect:
- Horizontal overflow.
- Navigation overlap.
- Calculator layout.
- History tables.
- Owner Settings sidebar.
- Document previews.
- Dialog dimensions.
- Floating WhatsApp button.
- Footer and 404 page.

Verify keyboard navigation, focus visibility, form labels, useful alt text, and readable contrast.

Test both light and dark themes.

Do not claim browser-based testing was completed if only static code inspection was performed.

## 12. SEO and Hosting Readiness

Verify:
- Page titles and descriptions.
- Open Graph metadata.
- Production URL configuration.
- `robots.txt`.
- `sitemap.xml`.
- No accidental localhost canonical URLs.
- Private application routes are excluded from the sitemap.
- Missing assets are reported.
- Static hosting route fallback is documented.
- Environment variables do not contain secrets.

Do not fabricate a production domain.

Do not promise indexing or search rankings.

## 13. Performance and Error Handling

Inspect for:
- Unnecessarily large images.
- Excessive dependencies.
- Unnecessary re-renders.
- Unhandled errors.
- Broken lazy loading.
- Layout shifts.
- Repeated analytics initialization.
- Crashes when optional settings are absent.

Improve performance only where the issue is supported by evidence.

Do not add unnecessary libraries or complex abstractions.

## 14. Acceptance Criteria

The application is ready for release only when:
- The production build passes.
- Available automated tests pass.
- Critical pricing calculations are verified.
- Existing data is preserved.
- Document generation is tested to the extent possible.
- Backup and restore are tested.
- No known critical defect remains unresolved.

If any criterion cannot be verified, report it as unverified rather than claiming full completion.

## 15. Final Report

Respond in Lao with these sections:

1. Summary of the audit.
2. Bugs found.
3. Fixes applied.
4. Commands actually executed.
5. Test results, including failures.
6. PDF and Lao-font verification status.
7. Data integrity and backup results.
8. Security limitations.
9. Remaining known issues.
10. Exact next actions required before public deployment.

List important files changed.

Do not fabricate test results, browser screenshots, build output, or deployment success.

Stop after the audit and fixes. Do not start another development phase automatically.
